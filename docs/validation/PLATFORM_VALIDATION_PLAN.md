# 跨平台、遮罩退出与睡眠计时验证方案

> 日期：2026-10-13  
> 状态：方案已编写，验证程序尚未开发，全部运行测试未执行。  
> 基线：[PRD 1.0](../requirements/PRD.md)、[实施计划](../../task_plan.md) T-02 至 T-06、T-15、T-22 至 T-25。

## 1. 验证思路与先后顺序

先制作最小平台验证程序，确认 GUI 框架与操作系统接入可行，再把同样的适配层接入正式提醒引擎。验证分为三个层次：

1. **自动化规则测试**：使用可控制的测试时钟，检查计时、合并、暂停、恢复、过期和去重。它证明计算规则，不能证明操作系统实际发送了睡眠事件。
2. **真实桌面验证**：运行真实应用包，检查 GPU 绘制、托盘、通知、多屏、焦点和锁屏/睡眠事件。
3. **最终包回归**：接入完整应用后，在相同目标环境重新检查关键路径、安装/升级/卸载和长期稳定性。最小程序通过不等于完整产品已经通过。

本方案细化已有验收门槛，不新增产品功能，不改变默认强制休息、紧急退出和双时钟语义。

## 2. 最少需要的设备

| 环境编号 | 设备与系统 | 用途 | 当前证据 |
| --- | --- | --- | --- |
| ENV-A | 当前 Apple M4、macOS 15.7.3 | 首次实现、Apple Silicon 原生运行 | 已核实系统与架构；应用未验证 |
| ENV-I | 支持 macOS 15 的 Intel Mac，运行 x86_64 包 | Intel CPU/GPU、通知、原生窗口与睡眠恢复 | 测试设备尚未确认 |
| ENV-W | Windows 10 22H2 x64 PC，有可用 GPU 驱动 | Win10 原生运行、系统托盘、遮罩和睡眠 | 测试设备尚未确认 |
| ENV-W11 | Windows 11 x64 PC | 后续兼容冒烟 | 测试设备尚未确认 |
| ENV-D | 外接显示器、连接线/扩展坞 | 双屏、混合缩放、拔插和主屏切换 | 测试设备尚未确认 |

优先使用已有或借用的设备，不需要立即购置整套设备。显示器可以在测试机器间复用。每个正式支持的系统/架构都至少执行一次双屏验证；在一台 M4 上测试双屏不能证明 Intel 或 Windows 的窗口行为相同。

没有对应机器时：

- 可用 CI 编译和运行独立核心测试，尽早发现类型、链接和条件编译错误。
- 可在 x64 宿主上的 Win10 虚拟机初测安装、托盘和通知，但标注虚拟 GPU/显示器环境。GPU、多屏和真实电源状态仍需目标硬件验证。
- 在 M4 上运行 Windows ARM 虚拟机或 x64 模拟环境，不能等同于 Windows 10 x64 原生兼容测试。
- 在 M4 上运行 x86_64 程序，即使 Rosetta 能启动，也不能替代 Intel Mac 原生实测。
- 远程借用机器可跑构建和基础操作；远程桌面可能改变显示器和 GPU 会话，睡眠还会断开连接。电源、外接屏与焦点测试优先由现场人员操作，并在本地记录日志，恢复连接后再取回。
- 缺失环境的测试标为“未执行/受设备阻塞”；可以继续独立模块开发，不能通过文字说明把兼容性状态改为“通过”。

## 3. 最小平台验证程序做什么

构建一份简单的诊断程序 `platform_probe`，使用准备采纳的固定 GPUI Kit/GPUI 版本，产出 Windows x64、macOS arm64 和 macOS x86_64 的原生包。运行机不需要 Rust 或源码。

| 操作 | 验证目的 |
| --- | --- |
| 显示平台、版本、进程架构、GPU 后端和显示器信息 | 证明当前测试的是哪一个目标与构建 |
| 显示主窗口、关闭后保留托盘、重新打开、退出进程 | 验证后台常驻生命周期 |
| 发送测试通知、点击后重新打开主窗口 | 验证应用身份、权限和通知响应路由 |
| “开始 30 秒遮罩” | 验证绘制、全屏、退出和自然结束 |
| “开始 3 分钟休息” | 留出足够时间进行真实锁屏/睡眠测试 |
| “开始 5 分钟提醒间隔” | 验证工作时间累计和恢复缓冲；不降低正式产品的最小间隔限制 |
| 显示时钟读数、锁屏/电源状态和事件日志 | 区分计算错误与系统事件接入错误 |
| 诊断构建中模拟某屏创建失败、重复系统事件 | 检查清理、降级与去重；故障注入开关不进入正常产品设置 |
| 导出本轮诊断记录 | 供其他机器执行后返回可分析的结果 |

原生时钟、事件和窗口适配代码优先复用进正式应用。探针中的临时计时演示只用于验证平台语义；正式状态机接入后再执行同一用例，不能让两套业务计时长期并存。

首次运行使用无正式个人记录的测试数据目录。遮罩仅在测试人员点击后触发；先证明退出有效，再测试多屏和睡眠。诊断日志不采集其他应用窗口内容、屏幕截图或键盘输入内容。

## 4. Windows 10 和 Intel Mac 怎样判断兼容

### 4.1 测试前记录

- OS 版本与构建号、CPU 架构、GPU/驱动、显示器与缩放、包版本与 SHA-256。
- 实际运行进程的架构；包文件名带 `x64` 不能作为架构证据。
- GPU 渲染后端是否正常、有无使用模拟/远程桌面环境。
- 通知权限、系统免打扰状态、应用安装位置及稳定应用身份。
- Windows 设备支持的睡眠类型；可用 `powercfg /a` 只读查询。记录 S3、Modern Standby/S0 或其他可用类型，不能将一种类型的通过推断成另一种已通过。
- macOS 通知使用真实 `.app` 包；Windows 使用计划中的应用身份/打包方式。`cargo run` 下的成功结果不替代包验证。

### 4.2 两个平台分别执行的基础清单

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| B-01 | 在目标系统打开对应 Release 包 | 窗口、中文字形、图标与按钮正常，无架构/系统 API/动态库/渲染错误 |
| B-02 | 关闭主窗口，再从托盘/菜单栏打开 | 进程和计时继续，入口可操作，没有第二个调度器 |
| B-03 | 发出系统通知，切到其他应用，再点击通知 | 在授权允许且系统展示时可见；点击回到本程序；未展示时可区分权限、免打扰、身份与适配问题，不假报送达 |
| B-04 | 进入遮罩，分别使用按钮、Esc 和倒计时结束 | 全部遮罩撤下，原桌面可操作；符合第 5 节时间与焦点要求 |
| B-05 | 执行第 6 节的锁屏与睡眠用例 | 间隔与休息两种时间语义正确，恢复不出现过期遮罩 |
| B-06 | 在无网络、无开发工具环境运行并明确退出 | 核心验证可执行；退出后无残留进程、窗口和提醒 |

M1 在真实包上检查 B-01 至 B-06。安装、覆盖升级、卸载和 8 小时稳定性在最终产品阶段执行，分别对应 PRD AT-21、AT-22。

## 5. 多屏遮罩与退出怎样验证

前置：两个显示器采用扩展模式，分别放置可点击的测试窗口；至少一组不同缩放比例。单屏退出已通过，测试人员知道所有屏幕都有退出按钮。

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| O-01 | 在单屏和双屏各启动 30 秒遮罩 | 全部活动屏幕覆盖普通应用，不能点击穿透；主交互面板在鼠标所在屏幕；每屏可见退出按钮 |
| O-02 | 分别点击主屏、副屏的紧急退出按钮 | 从按钮事件进入应用到整组窗口关闭 ≤ 1 秒；桌面恢复点击；只记一次中断 |
| O-03 | 遮罩获得焦点后按 Esc | 与 O-02 相同；焦点不在遮罩时不承诺全局 Esc 拦截 |
| O-04 | 等待 30 秒自然结束 | 所有屏幕结束同一场休息；各屏倒计时差 ≤ 1 秒；计时完成只结算一次 |
| O-05 | 在休息中拔掉副屏，随后接回；另一次拔掉主交互屏 | 计时不重启；剩余屏仍有退出入口；新活动屏正确加入；无残留透明窗口 |
| O-06 | 修改主屏、缩放和屏幕排列，测试屏幕位于主屏左侧/上方 | 无坐标偏移或未覆盖区域；退出按钮未被截断；显示器集合变化不会产生第二场休息 |
| O-07 | 在 macOS Space/全屏应用、Windows 虚拟桌面中启动并切换 | 记录正常用户桌面的实际覆盖行为；系统安全桌面不纳入遮罩范围；始终能回到可退出状态 |
| O-08 | 注入第二个显示器创建失败 | 撤下已创建的整组遮罩；同一实例降级为轻提醒；显示故障状态；不把部分覆盖记为成功 |
| O-09 | 结束后点击各屏下层测试窗口；明确退出或终止测试进程 | 下层输入正常，无隐藏拦截窗口；进程结束后所有遮罩消失 |

O-02、O-03、O-04 在每个目标架构重复至少 5 次，其中 O-02 覆盖每个屏幕。任意一次无法退出或残留拦截窗口均判失败，不用平均成功率掩盖。

退出速度使用连续时钟日志测量 `exit_requested → all_overlay_windows_closed`，同时通过实际桌面点击确认；应用自报“已关闭”不能单独证明窗口已释放。必要时仅录制测试桌面或用外部设备计时，验证窗口视觉消失时点。

## 6. 锁屏、睡眠和倒计时怎样验证

### 6.1 两种时间分别判断

- **提醒间隔**：只累计符合条件的使用时间，锁屏/睡眠期间不增加。
- **休息倒计时**：一旦开始，锁屏/睡眠期间仍经过。系统可能不运行应用代码，但唤醒后应立即依据连续时间判断是否完成。
- **工作日历**：决定当前是否在工作时段；与持续时间独立。不能直接用系统日期时间相减来实现前两者。

同一轮使用只有一个启用提醒、足够长且不中断的工作时段；边界用例另行配置。锁屏和睡眠分开做：屏幕关闭不是睡眠，锁屏也不自动意味着睡眠。

### 6.2 自动化规则测试

使用注入时间和事件在秒级完成大量场景：进入锁屏/睡眠、恢复、工作时段结束、跨日、时区变化、系统墙钟前后调整、重复唤醒和通知回调。对照 PRD S-01 至 S-16，断言预期状态与时间，不复制同一算法作为测试预期。

例如 5 分钟间隔运行 1 分钟后进入 2 分钟暂停，再恢复时应还剩 4 分钟。测试直接推进模拟时钟，无需真实等待 7 分钟；但实际系统适配仍要执行下一节的真实场景。

### 6.3 真实机器操作

手动执行时间以事件日志为准，下表为目标操作时间。提前保存测试人员的其他工作，随后通过系统正常菜单锁屏或睡眠。真实测试用外部秒表辅助，不以同一应用的剩余时间作为唯一基准。

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| C-01 | 5 分钟提醒运行约 1 分钟，锁屏约 2 分钟，再解锁 | 还剩约 4 分钟有效时间；没有把锁屏的 2 分钟扣掉；未触发恢复缓冲下限 |
| C-02 | 同 C-01，但让系统真正睡眠 | 结果同 C-01；系统电源记录需证明睡眠确实发生 |
| C-03 | 提醒仅剩 20 秒时锁屏，再解锁 | 按 PRD 恢复缓冲，新提醒至少等 60 秒有效时间，不在 20 秒后出现 |
| C-04 | 开始 3 分钟休息，约 30 秒后锁屏，约 60 秒后解锁 | 距离开始约 90 秒，还剩约 90 秒；恢复的是同一场休息 |
| C-05 | 开始 3 分钟休息，约 30 秒后睡眠约 2 分钟 | 距离开始约 150 秒，剩余约 30 秒；同一场休息不应用“新提醒等待 60 秒”规则 |
| C-06 | 开始 3 分钟休息，约 30 秒后睡眠约 4 分钟 | 唤醒时已完成，不再次显示或闪出旧遮罩；完成时间归属应为开始后 3 分钟，不是唤醒时间；只结算一次 |
| C-07 | 工作时段结束前 1 分钟开始 3 分钟休息，期间睡眠，时段结束后恢复 | 在工作时段结束时取消，不能记计时完成；下一时段完整计时 |
| C-08 | 工作时段结束前 5 分钟开始 3 分钟休息，期间睡眠，时段结束后恢复 | 休息先到时，仍记计时完成；与 C-07 不混淆；不补弹旧遮罩 |
| C-09 | 注入重复/乱序的锁屏、睡眠、唤醒、解锁事件；真实机器补做连续锁屏/睡眠/恢复 | 一个有效实例、一次结算、无负数间隔；锁屏仍有效时单独收到唤醒不得开始提醒 |
| C-10 | 注入墙钟前后跳变、时区变化，并在测试环境补做系统层检查 | 相同工作时段内的时长不被墙钟跳变改变；跨出时段按边界取消；历史日期不重写 |

C-01 至 C-08 在三类目标架构执行；至少将“恢复时未到时”和“恢复时已过期”两种睡眠场景各重复 3 次。Windows 设备只支持某种睡眠模式时，报告如实注明覆盖模式；休眠到磁盘等其他已支持且可用模式补充执行 C-02/C-05/C-06。

时长判断使用记录的实际进入/退出时刻计算，不要求人工恰好在整秒操作。恢复后显示剩余值与参考经过时长误差目标 ≤ 2 秒；可见倒计时允许按秒取整。验证 ≤ 1 秒撤罩时，从应用收到退出/恢复事件开始计量，单独记录 OS 派发事件的延迟。

### 6.4 如何证明机器真的睡了

- Windows 使用系统电源事件日志及设备支持的电源报告；Modern Standby 与传统 S3 分开记录。
- macOS 使用系统电源日志（例如只读检查 `pmset -g log` 中本轮的 sleep/wake 条目）。
- 记录系统睡眠区间、应用生命周期事件和时钟快照三者是否一致；日志只截取本轮必要字段。
- 如果只是屏幕熄灭、睡眠被其他进程阻止，或系统证据缺失，将本轮记为无效/需重跑，不记测试通过。

## 7. 记录与结果判定

每次测试输出一个本地报告目录，建议包括：

```text
run-<环境>-<时间>/
  environment.json   # 系统/架构/渲染后端/屏幕/构建/包校验和
  events.jsonl       # 本轮引擎和平台事件
  results.md         # 用例、预期、实际、Pass/Fail/Blocked/NotRun
  power-evidence.txt # 本轮必要睡眠/唤醒证据
```

事件记录最小字段：事件序号、实例/会话 ID、墙钟时间、连续时钟值、有效累计时间、状态转换、剩余时长、显示器标识、关闭开始/结束及错误码。隐私内容不写入日志。

首次验证矩阵全部保持“未执行”，执行后逐项填写：

| 环境 | 原生包启动 B-01 | 托盘/通知 B-02~03 | 遮罩退出 O-01~09 | 双时钟 C-01~10 | 系统电源证据 |
| --- | --- | --- | --- | --- | --- |
| M4 / macOS 15.7.3 | 未执行 | 未执行 | 未执行 | 未执行 | 未取得 |
| Intel / macOS 15 | 未执行 | 未执行 | 未执行 | 未执行 | 未取得 |
| x64 / Windows 10 22H2 | 未执行 | 未执行 | 未执行 | 未执行 | 未取得 |

**通过条件：**对应目标的必需用例有证据且通过，没有无法退出、残留遮罩、休眠错算或重复完成等核心缺陷。通知被用户禁用时，预期的“不可展示但程序正常、状态诚实”属于该拒绝场景通过，不等同于通知正常投递场景通过。

**失败处理：**记录环境、包、复现步骤、实际结果与日志，修复后复跑失败用例和受影响路径。若 GPUI Kit 的原生能力无法满足，先验证系统适配方案；确认仍无法满足后评估框架替代，不缩减 Intel/Win10 的已确认需求。

**执行顺序：**M4 单屏退出 → M4 双屏与睡眠 → Windows 10/Intel 原生包同套用例 → 汇总技术决策 → 正式引擎集成后回归 → 最终包与 8 小时稳定性。设备尚未到位时同步推进独立规则测试和存储开发，保留未验证标记。
