# OTA 自动更新文档

整理日期：2026-10-14。面向项目维护者与后续实施者。当前内容是技术调研、原理说明与建议设计，尚未接入更新器或部署更新服务。

## 结论

保留 Rust + GPUI，优先验证 Velopack 官方 Rust SDK，使用现有 GitHub Releases 托管更新包。需要自定义灰度时再加入轻量决策服务，更新包仍可放在 GitHub，无需额外部署对象存储或 CDN。

目标体验是首次安装后自动检查、后台下载，在用户确认或约定时机保存状态、退出并启动新版。原生代码需要重启应用生效，不需要重启操作系统。旧版本没有更新器，需要手动迁移一次。Linux 还需补齐本应用的平台适配与打包，不能用“更新框架支持 Linux”代替应用兼容性验证。

## 术语约定

- **OTA / 自动更新**：客户端获取更新内容并在本机应用，用户不必反复手工下载安装。
- **全量包**：目标版本完整的更新内容。
- **差分包**：需要结合旧包还原目标版本的变化数据；主要节省网络流量。
- **整体替换**：切换到完整的新应用目录、bundle 或 AppImage；可与差分下载同时使用。
- **热更**：容易有歧义。本文明确区分“重启生效的代码包更新”和“保持进程运行的代码热替换”；当前建议方案是前者的自动更新体验。
- **更新源**：版本清单和产物的获取方式，可以是 GitHub、HTTP 服务或自定义接口。
- **灰度**：只向部分合格安装提供一个目标版本，不等于发布一个 beta 标签。

## 实施顺序

1. 用真实应用的两个递增版本验证 Velopack + GitHub Releases，全量更新优先。
2. 完成签名、版本统一、数据保存、首次迁移及平台失败场景验证。
3. 按需接入安装 ID、指定名单、稳定分桶、安装前授权、暂停/撤回和后台统计。
4. 补齐 Linux 适配，验证 AppImage 更新；若要求三系统同时首发，将这一步前移。
5. 测量后决定是否启用差分、迁移托管服务或增加自动扩量。

平台签名、更新内容可信验证、数据库迁移与恢复需要单独验收。签名和 SHA 摘要不等价，更新完成也不自动意味着新版业务健康。详细边界以调研报告与平台设计为准。
