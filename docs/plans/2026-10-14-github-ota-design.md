# Velopack + GitHub Releases OTA 需求与设计

日期：2026-10-14（北京时间）。状态：需求澄清已完成；尚未开始实现。用户确认其余默认值，并明确排除额外的更新清单签名验证。

本轮目标是让现有 Rust + GPUI 应用通过 GitHub Releases 完成日常自动更新。本文是本轮范围与验收依据，收敛此前的 [OTA 调研](../research/OTA_UPDATE_RESEARCH.md) 和 [GitHub 分发方案](../ota/GITHUB_RELEASES.md)；历史调研中更广的建议不自动纳入本轮，[自建灰度平台](../architecture/OTA_PLATFORM_DESIGN.md) 不属于本轮范围。

任务分解、文件改动、技术验证与交付顺序见 [OTA 完整实现计划](../implementation/OTA_IMPLEMENTATION_PLAN.md)。实现计划已编写，代码实现尚未开始。

## 一、已确认的选择

| 项目 | 用户已确认的要求 |
| --- | --- |
| 更新方案 | Velopack + GitHub Releases；不购买或部署更新服务器 |
| 更新范围 | 正式发布后，所有使用兼容平台和旧版本的用户都可以获取更新；不做灰度 |
| 账号 | 不引入账号机制 |
| 平台 | Windows x64、Mac Apple Silicon、Mac Intel；首版不包含 Linux |
| 日常体验 | 自动检查、后台下载，用户明确点击重启更新后才安装 |
| 发布方式 | 推送 `release` 分支后自动构建草稿 Release，维护者验证后手动发布 |
| Windows 分发 | 安装版：首次运行安装程序，以后在应用内更新 |
| 当前签名条件 | 没有 Apple 正式代码签名证书和 Windows 代码签名证书 |
| 首版校验范围 | 不接入额外的更新清单签名与公钥验签；保留 HTTPS 和 Velopack 自带的包完整性校验 |
| 下载完成提示 | 弹出更新对话框，提供“立即重启”和“稍后” |
| 稍后行为 | 对同一版本，本次进程运行期间不再自动弹窗，下次启动再提醒 |
| 重启边界 | 下次启动只提醒，不因缓存包存在而自动安装；“关于小站”保留更新入口 |

“所有用户可更新”不表示强制更新，也不表示不同平台下载相同文件。关闭主窗口只会隐藏常驻应用，不算退出或下一次启动。

## 二、已确认的行为与范围

### 1. 检查与下载

- 启动进入可用状态后在后台检查；常驻期间每 12 小时检查一次，并加入随机抖动和请求限频，避免集中请求及短时间反复重启造成请求风暴。
- “关于小站”提供当前版本、更新状态、检查更新、下载进度、更新说明和重启更新入口。
- 提供“自动检查并下载更新”开关，默认开启；关闭后仍可手动检查和更新，已经下载的更新可由用户主动安装。
- 首版只接收公开的非草稿、非 prerelease 版本，并按安装包平台和架构选择版本；不提供 beta 渠道切换。
- 首版使用全量更新包。差分下载、断点续传优化、镜像站和 CDN 留待测量后决定，不作为本次交付要求。

### 2. 弹窗与重启

- 对话框展示目标版本、简短更新说明，以及“立即重启”“稍后”。同一版本在一次进程运行中最多自动弹出一次；关闭对话框等同“稍后”。
- 全屏休息、锁屏期间延后弹窗，恢复可交互状态后再提醒；下载完成不自行唤出主窗口或退出应用。
- 点击“立即重启”后，确认没有进行中的休息及未处理的设置草稿，等待已提交设置、记录和窗口状态成功写入，再正常退出、释放单实例锁、应用更新并启动新版。
- 未保存设置沿用现有保存／放弃／取消交互，不自动提交或丢弃草稿。保存失败或等待超时则取消此次更新退出，继续保留可用的旧应用并显示原因。
- 新版继续遵守菜单栏／托盘常驻行为；不因更新而重新出现首次引导，不重置用户设置、记录或悬浮窗偏好。

### 3. 离线与失败

- 网络失败、GitHub 限流或下载失败不影响本地提醒，也不显示成“已是最新版本”。自动检查失败只在更新区域记录状态，提供手动重试，后台采用退避重试。
- 无法直连 GitHub 时，本次不承诺自动更新可用；保留当前版本并提供发布页入口。首版不增加代理服务或下载镜像。
- 已下载且通过包完整性校验的完整更新，在离线时仍允许用户主动安装，不引入服务器安装授权。
- 校验失败、空间不足、目录不可写或文件被占用时停止安装，给出可操作提示。替换失败后的恢复必须实测；不承诺所有失败都能自动恢复。
- 问题版本优先发布更高版本修复，不提供自动降级或“新版启动失败后自动回退数据库”的能力。撤下 Release 不能追回用户已缓存的更新包。

### 4. 打包、版本与首次迁移

- Windows 使用 Velopack 用户级安装布局；Mac 保留 `.app` 体验，按 ARM64 和 Intel 分别提供 ZIP，使用稳定的应用标识。
- 沿用现有目标系统范围：Windows 10／11 x64，macOS 15+；实际支持以各目标机器的验收结果为准。
- 统一应用、安装包、更新清单和 Release 的版本来源；每次对用户发布都递增更新器可比较的版本，例如 `0.1.1 → 0.1.2`，不能只改构建序号。
- 当前已分发版本没有更新器，旧用户需手动安装一次带 OTA 的版本。保持原用户数据目录，并验证旧便携版到新 Windows 安装版、旧 Mac 包到新 Mac 包的数据保留和重复启动行为。

### 5. 平台签名条件与包完整性

- 本次不购买平台证书、不新增正式代码签名与公证流程，先在现有条件下验证 OTA。Mac 沿用必要的 ad-hoc 临时签名；Windows／Mac 首次安装或更新时的系统提示以实机验证记录为准。
- 用户明确选择不处理额外的签名验证：不生成更新签名密钥，不制作签名清单，不接入客户端公钥验签或密钥轮换。
- 使用 HTTPS，保留 Velopack 自带的包大小与摘要完整性校验，具体能力随选定 SDK／打包工具版本复核。包损坏或校验失败时不应用更新。
- 完整性校验用于检测下载内容是否符合清单，不等同于独立的发布者签名认证。本轮依赖 HTTPS 和 GitHub 发布仓库的访问控制，不声称具备额外的公钥信任验证。
- 系统自身的代码签名检查保持原状；更新器不自动关闭系统安全机制。正式签名、公证和额外的更新签名验证均不作为本轮交付门槛。

## 三、实现设计

### 组件和数据流

GitHub Actions 负责三种目标的构建、检查和 Velopack 打包，全部成功后汇总到同一草稿 Release。维护者检查安装与更新说明后手动公开；正式客户端只读取公开发布数据，不携带 GitHub 私人访问令牌。

客户端增加后台更新模块，由现有 GPUI 事件协调器接收状态、刷新“关于小站”和管理提示对话框。锁定兼容的 Rust SDK 与 `vpk` 版本，优先使用原生 GitHub 更新源，不为签名验证增加自定义更新源，也不增加后端 API。

```text
推送 release → 三目标构建与打包 → 上传草稿 → 维护者验证 → 手动公开
                                                          ↓
客户端后台检查 → 选择匹配版本 → 后台下载与校验 → 就绪弹窗
                                                   ├─ 稍后 → 保留缓存与入口
                                                   └─ 立即重启 → 保存成功 → 退出 → 更新器替换 → 新版启动
```

更新状态至少区分：空闲、检查中、无新版本、下载中、已就绪、保存与退出中、应用更新、失败。缓存包与提示记录绑定版本；损坏或丢失的缓存不能保持“可立即重启更新”的状态。

### 发布与隐私边界

- 普通客户端访问的 Release 附件必须能够匿名下载；仓库可见性及发布地址在实施前核实。草稿验证通过维护者下载产物或专用测试源进行，不让正式客户端访问草稿。
- 发布产物保持不可变，不覆盖已公开版本的同名附件；发布前确认三个目标包与清单均齐全。
- 不新增账号、灰度安装 ID、更新结果上报或行为追踪服务；更新状态与必要诊断保存在本机。访问 GitHub 仍会产生提供商正常的请求日志，不能宣称完全没有网络元数据。

## 四、首版验收标准

1. Windows x64、Mac ARM64、Mac Intel 各用两个真实递增版本，验证首次安装、发现更新、下载、重启替换及再次启动；构建成功不能代替实机通过。
2. 草稿发布期间正式客户端不可见；手动公开后可发现新版本；忽略 prerelease、旧版本和其他平台／架构产物。
3. 下载完成弹窗、“稍后”后的本次运行抑制、下次启动再提醒及“关于小站”主动更新均符合要求；普通重启不得偷偷安装缓存更新。
4. 全屏休息和锁屏期间延后提醒；保存失败时不进入替换；更新后设置、历史记录、应用身份与常驻行为保留。
5. 覆盖离线、GitHub 限流、下载中断、缓存丢失、包损坏／大小或摘要不符、空间不足、目录不可写、文件占用以及更新辅助程序无法启动等场景；额外的签名验证不在验收范围内。
6. 从 GitHub 实际下载首次发行包，记录各目标机器的系统提示和人工操作；没有正式证书的条件下，也要完成真实升级验证，不能只验证本地构建产物。
7. 验证已有手动安装用户的一次性迁移；在隔离数据目录中检查数据保留，避免用正式用户数据做破坏性演练。

需求澄清在此完成。后续实现以本文为依据；实现前复核仓库匿名下载条件、SDK／打包工具兼容版本以及目标实机资源，这些技术核实不改变已确认的产品范围。
